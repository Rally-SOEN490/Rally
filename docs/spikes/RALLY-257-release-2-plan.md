### #92 RALLY-70: Set a match format (Iteration 6)

**User story**
As an organizer, I want to set how matches are played, so that scores and timing follow my tournament's rules.

**Acceptance criteria**

- [ ] A match format has a mode (best of, fixed sets, timed), sets per match, points to win a set, the deciding-set target (best of only), win by 1 or 2, an optional point cap, a time limit (timed only), set length, time between sets and warm-up.
- [ ] Defaults are filled in: pools play 2 sets to 25 (cap 27); playoffs play best of 3 to 25 (cap 27) with the third set to 15 (cap 17).
- [ ] Values are checked: positive whole numbers, an odd number of sets for best of, and caps higher than the points to win.
- [ ] Formats are saved with the pool or playoff round that uses them.
- [ ] The screen shows how long each match books a court, and when the day would end with the tournament's courts.
- [ ] PO approval

**Risk**
Medium. Scores and the schedule both depend on this. Check: unit tests for every validation rule and for the time estimate, plus an API test that rejects an invalid format.

**Task plan**

- [ ] Add the `MatchFormat` table and its link to pools and playoff rounds (migration; see docs/architecture/scheduling.md §5)
- [ ] Move `match-format.ts` from the spike into the tournaments module, with its tests
- [ ] API: create, read and update a format; only the tournament's organizer
- [ ] Screen: match format form with Pools and Playoffs tabs (mockup 1)
- [ ] Show the court time and estimated end of the day
- [ ] Translations, plus loading and error states

**Related references**
Spike #362. Mockup: docs/mockups/scheduling-wireframes.html, screen 1.

### #105 RALLY-83: Generate a suggested schedule (Iteration 7)

**User story**
As an organizer, I want the app to suggest a schedule once teams have signed up, so that I don't build it by hand.

**Acceptance criteria**

- [ ] Scheduling is available after registration; it isn't part of creating the tournament.
- [ ] The schedule uses the tournament's start and end times, number of courts and match time estimates.
- [ ] All divisions share the tournament's courts.
- [ ] No team plays two matches at the same time, and no court holds two matches at once.
- [ ] Pool matches come before playoff matches, and a playoff match comes after the matches that feed it.
- [ ] If everything doesn't fit, the organizer is told which matches don't fit.
- [ ] The same teams and settings always give the same schedule.
- [ ] PO approval

**Risk**
Medium (was High). The algorithm is decided: greedy slotting (docs/architecture/scheduling.md §3). Remaining risk: real tournaments with uneven pools or several divisions. Check: tests for 12 teams on 3 courts, two divisions sharing courts, a day that's too short, and odd pool sizes.

**Task plan**

- [ ] Add the `Schedule` and `ScheduleSlot` tables (migration)
- [ ] Move `generate.ts` and `check.ts` from the spike, with their tests
- [ ] Read the matches from #361's tables and save the result as the draft schedule
- [ ] API: generate the draft schedule; only the tournament's organizer
- [ ] Screen: inputs, Generate button and result (mockup 2), grid on web and list on phone
- [ ] Show what doesn't fit and what to change

**Related references**
Spike #362. Depends on #361. Mockup screen 2.

### #292 RALLY-216: Edit the schedule (Iteration 7)

**User story**
As an organizer, I want to edit the suggested schedule, so that I can fix anything I don't like.

**Acceptance criteria**

- [ ] The organizer can move a match to another time or court, or swap two matches.
- [ ] The organizer can lock a match, so regenerating keeps it where it is.
- [ ] The app shows conflicts right away: a team playing twice at once, a court already used, a time outside the tournament, or a playoff before the matches it waits for. Too little rest is a warning.
- [ ] Changes are saved as a draft until published.
- [ ] A match with a confirmed score can't be moved.
- [ ] PO approval

**Risk**
Medium. Edits can create conflicts and change times that players have already seen. Check: conflict tests for each rule, and the server re-checks every change.

**Task plan**

- [ ] API: move, swap and lock a slot, returning the schedule's problems
- [ ] Regenerate around the locked matches (extends `generate.ts`)
- [ ] Screen: select a match, then the move sheet on phone and drag on web (mockup 3)
- [ ] Problems panel with errors and warnings

**Related references**
Spike #362. Drag and drop options from #361. Mockup screen 3.

### #293 RALLY-217: Publish the schedule (Iteration 7)

**User story**
As an organizer, I want to publish the schedule, so that players can see when and where they play.

**Acceptance criteria**

- [ ] Publishing makes the schedule visible to players.
- [ ] A schedule with errors can't be published; warnings need the organizer to confirm.
- [ ] Publishing again after changes replaces the previous version.
- [ ] Publishing triggers the schedule notification.
- [ ] PO approval

**Risk**
Low. Publishing a schedule with conflicts would expose errors. Check: the server checks for conflicts before publishing, and tests show players see only the published version.

**Task plan**

- [ ] API: publish copies the draft into the published schedule in one transaction and adds one to its version
- [ ] Block publishing on errors on the server too
- [ ] Hook into the notification from #343
- [ ] Publish button and confirmation dialog

**Related references**
Spike #362. Notifications: #343.

- [ ] PO approval

Use a clean, neutral style with rounded cards, a single accent color and clear red (error) and amber (warning) states. Use sentence case for all text.
>

## Presentation outline (about 5 minutes)

1. **The problem (30 s).** After registration, the organizer needs a schedule: which match, on which court, at what time. Today they build it by hand.
2. **Match formats (1 min).** The options we support (best of, fixed sets, timed, caps, win by 2), the defaults, and how court time is estimated (0.9 min per point). Forfeits are stored as a result type and count as sets won 25-0.
3. **Algorithm (1.5 min).** The comparison table: greedy vs. a constraint solver. Why greedy: it fits our TypeScript stack, it's deterministic, and it says what doesn't fit.
4. **Demo (1 min).** Run the tests, then show the 12-team schedule: the defaults don't fit (the final is reported), sets to 21 fit and end at 19:50. Key insight: courts are the bottleneck, so the format screen shows the estimated end of the day.
5. **Mockups (1 min).** The 4 screens, phone and web.
6. **Plan and questions (30 s).** The Release 2 table above, and the questions for Chau, #361 and #363 (scheduling.md §6).

Demo commands. The scheduling tests don't use the database, but the repo's Vitest setup migrates the test database before any test, so PostgreSQL must be running:

```bash
docker compose up -d postgres              # from the repo root
cd apps/api && npx vitest run test/scheduling.test.ts
```
